# M3 Tracking + AWS Staging Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Courier GPS reaches the customer's tracking page as a privacy-safe live snapshot in under a second (p95):
- partners can read courier position, trail and proof points for disputes;
- a sandbox simulator drives deliveries end to end;
- all of it runs on a lean AWS staging environment built from an empty account.

**Architecture:**
- **`tracking`** becomes a full onion service.
  - It keeps an event-fed read model of deliveries, couriers and tenant settings.
  - It ingests fixes over an internal Connect RPC from the gateway.
  - It holds each delivery's live **state** in Redis. Two pure projections build what each audience gets: the viewer **snapshot** (visibility rules) and the unfiltered **partner view**.
  - Viewers get snapshots over WebSocket/SSE fanned out through Redis pub/sub.
  - Fixes go to a day-partitioned Postgres trail off the hot path.
- **`gateway`**:
  - issues tracking links and Ed25519 viewer JWTs (JWKS published);
  - mounts the viewer session routes with CORS;
  - routes the relay, partner tracking-data and simulate calls to tracking.
- **`deliveries`** gains `ready_at` and applies `arriving` from `tracking.arrival_detected`.
- **AWS:** OpenTofu stacks set up the Organization and a lean staging environment (one ECS-on-EC2 host, RDS, ALB). GitHub Actions deploys there through OIDC.

**Tech Stack:** carried over from M2: Go 1.27.3, pgx v5, sqlc, Connect v2, NATS JetStream, Redis 8.2, PostgreSQL 18 + PostGIS 3.6, testcontainers-go, `pgregory.net/rapid`. New:
- `github.com/coder/websocket` (WebSocket server and test client);
- `github.com/golang-jwt/jwt/v5` (EdDSA JWTs);
- OSRM `osrm/osrm-backend` (pinned by digest in compose) with `osmium-tool` for extracts;
- OpenTofu ≥ 1.10 (S3 native locking);
- `trivy config` for IaC scanning.

Pin each with `go get <module>@latest` (or the latest release) at the time of the task, and record the version in the commit.

## Global Constraints

- All Global Constraints of the M0–M2 plans still apply. Work happens on branch `m3-tracking` (created from `main`; the design commit on `m3-planning` is cherry-picked or merged first).
- **New ID prefixes in `pkg/ids`:** `tl` (tracking link), `fix` (not exposed; trail row ids are bigint), `sim` (simulation run).
- **Visibility** (spec §4.5) is computed only in `tracking/internal/domain`. The viewer snapshot has `courier: null` whenever the courier is hidden, and `route.to_pickup: null` in `direct`. There is no other code path that serializes courier position to a viewer.
- **Signal states:**
  - `pending`: visible, no fix yet;
  - `live`: last fix ≤ **30 s** old;
  - `stale`: > 30 s;
  - `lost`: > **5 min**, or `pending` for > 5 min.
  All four are in the contract from the start.
- **ETA:**
  - `eta_state`: `calculating | estimated | live`.
  - Before pickup the window is `eta_window {min_seconds, max_seconds}` = ETA ± **300 s** (min clamped ≥ 0), with `eta_seconds` the midpoint.
  - After pickup `eta_window: null`.
  - ETA is recomputed at most every **10 s** per delivery; reroute at > **50 m** off-route.
  - `tracking.eta_changed` fires on changes of ≥ **120 s**, at most once per **60 s**.
  - `eta_quality: "estimated"` marks an OSRM fallback.
- **Ready time:** `ready_at` (per delivery, may change until `picked_up`) → else `created_at + default_prep_minutes` (tenant setting, `null` = unset, range 1–240) → else unknown.
  - `ready_at` must be ≥ `created_at − 1 h` and ≤ `now + 24 h`, else `400 validation_failed`.
- **Arrival:** within ≤ **200 m** of the dropoff, or ETA ≤ **90 s**, publish `tracking.arrival_detected` once per delivery.
- **Ingest:**
  - Fix shape `{t, lat, lng, accuracy_m, speed_mps?, heading_deg?}`. A batch holds ≤ **50** fixes and ≤ **16 KB**.
  - `t` must be ≤ receipt + **5 s**. Fixes older than receipt − **2 min** are stored in the trail but never move the live position.
  - Plausibility: ≤ **200 km/h**, and no jump > **1 km** in < **10 s**. Implausible fixes are dropped and counted.
  - A fix is accepted only while the courier has ≥ 1 non-final assigned delivery, and it is attached to each such delivery.
  - Response `{accepted, dropped}`.
- **Relay rate limits:** `rl:relay:cou:<cou_id>` **1/s burst 5**, plus `rl:relay:ten:<tenant>:<env>` **500/s burst 1000**, separate from `rl:sk:*`.
- **Viewer rate limits:** `POST /v1/tracking/session` and `/refresh`: **10/min per IP** (`rl:viewer:ip:<ip>`) and **30/min per link** (`rl:viewer:tl:<tl_id>`).
- **Tracking link:**
  - The token is 16 random bytes, base64url without padding (22 chars). It is stored as HMAC-SHA256 with the gateway pepper.
  - URL `${TRACKING_URL_BASE}/t/<token>`.
  - `expires_at` is `null` until the delivery is final, then final `occurred_at` + **30 min**.
  - Rotation revokes the old link immediately.
- **Viewer JWT:**
  - EdDSA (Ed25519). Header `kid`.
  - Claims: `iss: "dt-gateway"`, `aud: "viewer"`, `sub: <del_ id>`, `tid`, `env`, `lid: <tl_ id>`, `iat`, `exp = iat + 15 min`.
  - Keys come from `VIEWER_SIGNING_KEYS` (`kid:base64(32-byte seed),…`) plus `VIEWER_SIGNING_KEY_CURRENT`, the same format as `DATA_KEYS`.
  - JWKS is at public `GET /.well-known/jwks.json`. Tracking caches it for 5 min and refetches on an unknown `kid`.
- **Revocation:**
  - Redis key `dt:viewer:revoked:<tl_id>` with TTL **15 min** (the JWT lifetime).
  - Redis channel `dt:viewer:revocations` (payload `tl_id`). Tracking closes matching streams with message `{type:"revoked"}` and WebSocket close code **4401**.
- **Snapshot `version`** is per delivery: `max(previous + 1, unix_ms(now))`. It stays monotonic even if Redis is flushed and the state is rebuilt.
- **Retention:**
  - raw fixes **30 days**, then simplified with Douglas–Peucker at **5 m** tolerance;
  - simplified routes, proof points and delivery records (tracking and deliveries) **13 months**;
  - jobs run nightly at 02:00 UTC and are idempotent;
  - on `delivery.personal_data_erased` the raw trail is replaced by the simplified route at once.
- **Proof points** for `at_pickup`, `pickup_confirmed`, `arriving`, `delivered`, `failed`: the latest fix with `t` within **2 min** before the status `occurred_at`, else `position: null`.
- **Read audit:** `trail` and `proof-points` GETs write an audit row (`Action` = route name); `GET …/tracking` does not.
- **New problem codes:**

  | Code | Status |
  |---|---|
  | `link_invalid` | 401 (unknown, rotated or expired link token) |
  | `viewer_token_invalid` | 401 |
  | `simulation_state` | 409 |
  | `tracking_unavailable` | 503 |

  A delivery of another tenant or environment is `404 not_found`.
- **Streams:**
  - New `TRACKING` stream, owned and defined by tracking only (pattern D23/OQ22): subjects `tracking.>`, file storage, 2 min duplicate window, max age **7 days**.
  - Event types: `tracking.arrival_detected`, `tracking.eta_changed`, `tracking.courier_signal_lost`, `tracking.courier_signal_restored`, `tracking.snapshot_updated` (not published in M3; reserved), `courier.location_reported` (sampled 1/min per courier).
  - Consumers wait with `outbox.WaitForStream`.
- **Data on staging:** sandbox and simulated only. AWS budget **€82/month before VAT** (≈ €100 with VAT), across all accounts.
- **No long-lived AWS keys anywhere.** Humans use IAM Identity Center; CI uses OIDC.

## Review Focus

1. **A courier on two active deliveries** (End-to-end batching). One fix updates both deliveries. Each applies its own visibility: the Direct one before pickup stays hidden while the other shows the courier. Test: Task 5 `TestFixFansOutToEachActiveDelivery`, Task 3 `TestVisibilityIsPerDelivery`.
2. **A courier reassigned before pickup.** The old courier's later fixes must never move the new delivery's marker, and the new courier starts `pending`. Test: Task 5 `TestReassignmentDropsOldCourierFixes`.
3. **A relay batch with delayed or out-of-order `t`** (a partner backend replaying a buffer). The trail keeps all plausible fixes. The live position only advances on a newer `t`, and an old batch never flips `stale` back to `live`. Test: Task 3 `TestOlderFixNeverMovesLivePosition`, Task 5 `TestDelayedBatchKeepsSignalStale`.
4. **A delivery finishing (or the link rotated) while a viewer is connected.**
   - Final state: the courier disappears in the very next snapshot, and the stream stays open until the link expires, then closes.
   - Rotation: the stream closes within 1 s with `revoked`.
   Test: Task 8 `TestFinalStateHidesCourierThenClosesAtExpiry`, `TestRotationClosesOpenStreams`.
5. **Tracking restarts or Redis is flushed mid-delivery.** The state is rebuilt from Postgres (read model + latest trail fix), and the next snapshot's `version` is greater than any the viewer saw. Test: Task 5 `TestStateRebuildKeepsVersionMonotonic`.

  - window ± 300 s; state `estimated`;
  - no ready time → all `nil`, state `calculating`.
- **`picked_up`/`arriving`:** eta = `ToDropoffSec` (recomputed from the courier position by the app layer), window `nil`, state `live`.
- **Final:** all `nil`, state `live`.

## Decisions made in this plan (Claude's calls; review these)

| # | Decision | Why |
|---|---|---|
| P1 | **Ready time and default preparation time live in `deliveries` and `accounts`; tracking only reads them from events.** | The existing event-fed read model pattern keeps ownership clear (C1). |
| P2 | **The viewer JWT is renewed with `/tracking/session/refresh`,** and revocation goes through a Redis deny-list plus pub/sub. | Immediate cut-off with no NATS round trip; nothing on the viewer side needs the link token again. |
| P3 | **JWKS is public at `/.well-known/jwks.json`.** | Public keys aren't secret. It avoids a new internal RPC, and partners could verify viewer tokens later. |
| P4 | **Live state in Redis with CAS on a time-based version.** Postgres holds the read model and trail, written off the hot path, and buffered trail rows can be lost on a crash. | Meets p95 < 1 s. Spec §8.3 already treats pings as loss-tolerant. The version stays monotonic after a Redis flush. |
| P5 | **mTLS for all internal RPCs, not only accounts.** Certs come from env, and dev runs without them unless generated. | One mechanism, the same effort, and security first. |
| P6 | **KMS wrapping of `DATA_KEYS` = Secrets Manager under a customer-managed KMS key, injected by ECS.** | Envelope encryption with no AWS SDK in the services; rotation stays as in the runbook. |
| P7 | **Dev and CI use an Amsterdam clip of OSM; staging uses Noord-Holland.** OSRM uses MLD. | CI time and memory; staging covers the pilot region on a 4 GB host. |
| P8 | **One ECS-on-EC2 `t3.medium`, no NAT, Redis and NATS as containers, RDS single-AZ, a night and weekend schedule.** Fallback: Caddy instead of the ALB if the cost estimate exceeds €82. | Fits ≈ €100 with VAT (design §7.3). The owner is told before any size change. |
| P9 | **Partner guides go in `docs/guides/` as Markdown** until the Starlight site exists (M8). | Docs ship with the milestone (spec §15) without building the website early. |
| P10 | **The simulator runs in-process in tracking** and drives deliveries through the same RPCs as real traffic (with `actor: courier` added to `ReportEvent`). | The demo exercises the real paths; no separate simulator service. |
